# Machine-learning design

How WG-Match recommends rooms, and why we built the model this way. This
document describes the model in `core/ml_model.py` and how it feeds ranking in
`core/matching.py`.

## 1. What the model predicts

A **binary classifier** that estimates, for a (seeker, WG) pair, the probability
that the match will **succeed — that both sides accept**.

- **Label:** a match is a success (`1`) when its status reaches `accepted`, and a
  failure (`0`) when it is `declined`. Only resolved matches are used; `open` and
  `offered` matches are still undecided.
- **Why this label:** it is a real, logged outcome of the platform, not a survey.
  Our earlier design predicted satisfaction from a questionnaire ~3 months after
  moving in — data we would almost never actually collect. Match outcomes arrive
  within days, in volume, and describe a genuine success (a placement).

## 2. Features

For each pair we use the **eight lifestyle-slider differences**, scaled to 0–1:

```
feature[k] = |seeker[k] − wg_average[k]| / 10
```

The model only sees *how far apart* the seeker and the WG are on each trait
(tidiness, sociability, noise tolerance, guests, sleep rhythm, cooking together,
cleaning schedule, time at home). A WG's value on each slider is the **average of
its members' answers** (`database.get_wg_lifestyle_profile`). Missing answers stay
NaN and are imputed to the neutral mid-point (0.5).

## 3. The model: logistic regression

We use **scikit-learn `LogisticRegression`** (`class_weight="balanced"`), inside a
pipeline with a `SimpleImputer`.

**Why logistic regression over a random forest:**

- **Interpretable.** It produces one coefficient per lifestyle factor, so we can
  say *which* factors drive a successful match.
- **It learns our weights for us** (see §4) — the coefficients plug directly into
  the compatibility score.
- **Well-calibrated probabilities**, which matters because the probability is
  mixed into ranking (§5).
- **Robust with limited data** and hard to overfit — right for a course-scale
  dataset.
- In testing it **matched the random forest** on ROC AUC while being far easier
  to explain.

The relationship is a good fit: the features are already *differences*, and the
intuition "bigger gap → lower chance of success" is monotonic, which is exactly
what logistic regression models well.

## 4. Learned weights → the compatibility score

The compatibility score (`matching.compatibility_score`) is a weighted similarity
of the sliders. Previously every factor was weighted equally. Now the model's
coefficients are turned into **one positive importance per factor**, normalised so
the average weight is 1.0, and these weight the score — so ranking *learns* which
factors matter.

Example from the demo seed data:

| Lifestyle factor | Learned weight |
|---|---|
| Cooking together | 1.40 |
| Guests | 1.27 |
| Sleep rhythm | 1.26 |
| Sociability | 1.05 |
| Tidiness | 0.85 |
| Noise tolerance | 0.81 |
| Time at home | 0.71 |
| Cleaning schedule | 0.65 |

When no model is trained yet, ranking falls back to **equal weights** (the neutral
baseline), so a fresh install still works.

## 5. How it ranks

In `matching.rank_wgs_for_seeker` / `rank_seekers_for_wg`:

- **Lifestyle score** = weighted slider similarity, 0–100 (using the learned
  weights).
- **With a trained model:** `final = 0.8 × lifestyle + 0.2 × (match_probability × 100)`.
- **Without a model / too little data:** lifestyle similarity alone.

Hard filters (budget, move-in date, travel time, smoking, gender preference) are
applied first; the model only ranks candidates that already qualify.

## 6. Evaluation

We use **repeated held-out-seeker cross-validation** (`GroupShuffleSplit`,
25 folds, 20% test). Holding out *whole seekers* means a seeker's repeated matches
never appear on both sides of a split, which prevents data leakage. The reported
metrics are **averaged over the folds**, so they are stable rather than an
accident of one split. We report accuracy, a majority-class baseline, balanced
accuracy, ROC AUC and Brier score, then refit the final model on all resolved
matches.

**Example metrics on the demo seed data** (191 resolved matches, 45% accepted):

| Metric | Value |
|---|---|
| ROC AUC | 0.77 |
| Accuracy | 0.68 |
| Majority baseline | 0.55 |
| Balanced accuracy | 0.68 |
| Brier score | 0.20 |

The model clearly beats the baseline on both AUC and accuracy.

> **Caveat:** the demo outcomes are generated by the seed script from lifestyle
> similarity (plus noise), so these numbers describe the demo dataset and do not
> establish performance with real tenants.

## 7. Continuous learning

Every resolved match is a new training row, so the model improves as the platform
is used:

```
matches happen → outcomes logged (accepted/declined)
      ↑                                   ↓
rankings improve  ←  retrain  ←  more training data
```

Retraining (the **Train / refresh model** button in Insights, or
`python -m core.ml_model`) refreshes the learned weights and recalibrates the
probabilities, so the order future users see reflects what has actually worked.

**This is not automatically "always better" — three caveats we acknowledge:**

1. **Feedback-loop bias.** The ranking decides who is shown, which shapes the next
   batch of training data; low-ranked candidates get fewer chances to prove the
   model wrong. A small amount of exploration (not only showing the very top)
   keeps the data honest.
2. **It learns preferences, including biased ones.** We limit the model to the
   eight lifestyle factors — never gender, photos or names — and sanity-check that
   each learned weight points the sensible way ("bigger gap → worse").
3. **Retrain with a gate.** Each retrain re-runs the held-out evaluation; a model
   is only kept if it still scores well.

At course scale the data is small, so gains are gradual — the *architecture*
supports continuous improvement; with real scale the weights would keep
sharpening.

## 8. Where it lives in the code

| Concern | Location |
|---|---|
| Training label (resolved matches) | `database.get_training_data()` |
| Model, training, evaluation, weights | `core/ml_model.py` |
| Learned weights used in the score | `matching.compatibility_score` (weights arg) |
| Ranking blend and fallback | `matching.rank_wgs_for_seeker` / `rank_seekers_for_wg` |
| Metrics + learned-weights display | `views/insights.py` |
| Demo outcomes | `data/seed_data.py` (each match resolved to accepted/declined) |
